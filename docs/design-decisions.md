# 关键设计取舍

本文记录影响系统可靠性、可维护性和研究质量的关键取舍。

## 可信证据型研究，而非通用聊天

系统提示词和行业研究 Skill 要求：

- 优先使用私有研报和公开一手来源。
- 标明信息截止日期与来源日期。
- 区分历史事实、机构预测、预测修订和模型判断。
- 核对单位、币种、地域、财年/自然年和产品规格。
- 对关键数值和 CAGR 进行复算。
- 不把相关性包装成确定因果。
- 在交付前检查引用、矛盾、缺失信息和风险。

Skill 在当前用户轮内确定性选择并瞬态注入，不跨轮隐式继承。这样能够保持运行时简单，
同时要求用户在需要研究报告时于同一轮明确任务和交付格式。

## PDF 解析

金融研报常见双栏、表格、页眉页脚和扫描页。单纯按字符提取容易造成阅读顺序错乱、
表格断裂和页码丢失。

当前方案：

- 普通文字型 PDF 使用 PyMuPDF 读取带坐标文本块并恢复阅读顺序。
- 表格使用 pdfplumber 提取并转为 Markdown，尽量整块保留。
- 复杂、扫描、图像密集或本地解析质量不足的 PDF 路由到 Docling。
- 所有解析器输出统一的 `ParseResult` / `ParsedChunk` 契约。

代价是建库链路更复杂，但可以把 OCR 和在线检索资源隔离。

## 混合召回与精排

BM25 擅长股票代码、公司名、指标和产品型号等精确匹配；向量检索擅长语义近似。
系统并行执行两路召回，使用 RRF 融合去重，再由 Cross-Encoder 精排。

```text
BM25 Top-K ─┐
             ├→ RRF → Filter → Reranker → Top-N
Vector Top-K ┘
```

Reranker 候选数量按设备档位限制，避免 CPU 环境延迟失控。最终是否提高候选数，应以
Recall、MRR、nDCG 和 P95 延迟的联合评测为依据。

## 语义缓存

低相关结果如果被长期缓存，会把一次错误判断固化。因此写入缓存由精排置信度门控：

| top score | 策略 |
|---|---|
| 高于可信阈值 | 正常缓存 |
| 低相关但非空 | 不缓存 |
| 空结果 | 使用较短 TTL，允许后续重试 |

缓存不是证据来源。最终报告仍应引用原始文件或公开页面。

## 工具调用协议

模型可能把格式不合法的复杂工具参数放入 `.invalid_tool_calls`。如果路由只检查
`.tool_calls`，就会误判为“没有工具调用”，并可能把悬空调用写入 Checkpoint，导致
下一轮恢复后出现 Provider 400 错误。

因此协议检测统一覆盖有效与无效 tool call，并在三个位置执行：

1. 路由判断；
2. 模型输入前的消息修复；
3. 预算或异常退出时的 ToolMessage 闭合。

协议完整性优先于继续尝试工具。

## 分离业务预算与图熔断

`MAX_MODEL_ROUNDS`、`MAX_TOOL_BATCHES`、`MAX_TOOL_RETRIES` 和
`RAG_CALL_LIMIT` 表达业务预算；`RECURSION_LIMIT` 只防止图异常循环。

剩余步骤判断拆成多个函数，是因为它们位于不同生命周期位置：

- 模型调用前，需要为工具、结果处理和最终总结预留步骤。
- 工具节点入口，需要再次确认工具执行后仍能安全收口。
- 工具处理后，需要判断继续循环还是立即总结。
- 调度最终节点前，需要确认还容得下独立总结步骤。

这些函数共享同一设计目标，但前置状态和所需余量不同。分开命名可以让每个节点表达自己
的局部不变量，也便于针对边界值独立测试。

## RAG 配额与连续未命中

`RAG_CALL_LIMIT` 是当前用户轮的独立 RAG 次数上限；其他工具不会直接扣减它，但会
共享工具批次和图步骤预算。

`CONSECUTIVE_FAILURE_THRESHOLD` 统计连续
`has_relevant_content=False` 的 RAG 结果。达到阈值后继续改写相似查询通常收益很低，
因此 Agent 停止检索、说明证据不足并收口。一次有效 RAG 结果会中断连续未命中序列。

这与工具异常重试不同：执行错误由 `MAX_TOOL_RETRIES` 控制，无相关内容由连续未命中
阈值控制。

## 上下文管理

上下文预算按优先级处理：

1. 保留固定系统约束和当前问题。
2. 保留当前轮工具协议外壳。
3. 压缩或投影较旧的工具正文。
4. 按完整轮次移除更早历史。
5. 缩短证据摘录，但尽量保留来源元数据。
6. 仍然超限则在调用 Provider 前明确失败。

本地 Token 估算是确定性的近似值，不冒充 Provider 的精确计数。配置真实上下文窗口后，
系统还会预留输出 Token 和安全余量。

## Knowledge Service 单写者

Chroma/HNSW、BM25 和 Chunk Store 由单 Worker Knowledge Service 持有。Agent、MCP 和
评测通过 HTTP 客户端访问，不直接加载 Embedding/Reranker，也不打开索引文件。

这样减少多进程争用和缓存失效不一致，代价是增加一个服务边界和网络调用。Transport
Schema 与 Codec 集中维护，避免 Client 和 Server 各自重建领域对象。

## FastAPI 服务护栏

服务层包含：

- API versioning
- request_id 全链路追踪
- problem+json 错误体
- API Key 鉴权
- 匿名 IP 固定窗口限流
- per-user 每日 Token 预算
- token 级 SSE
- 断连取消上游执行
- Prometheus 指标
- FakeAgent/fakeredis 离线回归

流式接口发生错误时仍按协议发送 `error` 和 `done`，让客户端能够稳定关闭状态。

## MCP 生命周期

MCP 启动入口保持轻量，不在 stdio 握手阶段预热 Embedding、Reranker、Chroma 或 Redis。
首次业务查询由 Knowledge Service 按需预热。

普通客户端默认只看到必要工具；健康检查和显式预热属于管理能力，通过环境变量开启。
MCP 应用显式持有远程 Runtime，并在 stdio 退出后释放连接，不依赖模块级服务单例。
